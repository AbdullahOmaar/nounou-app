# تطبيق الموبايل الأصلي للطاقم (3A-412)

الويب الحالي نفسه يعمل داخل غلاف [Capacitor](https://capacitorjs.com) على
أندرويد/iOS — لا إعادة كتابة. الهدفان: إشعارات دفع موثوقة (نقطة ضعف الـPWA)
ومسح QR أسرع/أوثق عند البوابة.

- **App ID:** `com.nounou.staff` — **اسم العرض:** `Nounou Staff`
- **الإعدادات:** `capacitor.config.ts` (webDir = `dist`)

## التشغيل والتطوير

```bash
npm run build          # بناء الويب إلى dist
npx cap sync           # نسخ dist + تحديث الإضافات في المشروعين الأصليين
npx cap open android   # فتح Android Studio (يتطلب Android SDK + JDK)
npx cap open ios       # فتح Xcode (يتطلب macOS)
```

بناء APK/AAB فعلياً يحتاج Android SDK + JDK على جهاز البناء — بيئة CI
الحالية لا توفرهما؛ توليد المشروعين والمزامنة يعملان في أي بيئة Node.

## ملاحظات تقنية

- الكشف عن البيئة الأصلية مركزي في `src/lib/native.ts`
  (`Capacitor.isNativePlatform`) — على الويب كل المسارات الأصلية معطلة
  ولا يتغير أي سلوك قائم.
- إضافة `@capacitor-mlkit/barcode-scanning` على iOS: لا توفر
  `Package.swift` (تحذير SPM وقت المزامنة) — تُربط عبر CocoaPods.
- ملفات اعتماد FCM ‏(`google-services.json` / مفتاح APNs) تُضاف وقت
  إعداد مشروع Firebase/المتاجر — **لا تُخزَّن أي أسرار في هذا المستودع**.
- **⚠️ تحذير إعادة التوليد (ملاحظة QA على PR #91):** كبت Semgrep المبرر
  على `android:exported` في `android/app/src/main/AndroidManifest.xml`
  يعيش داخل ملف مولّد — أي `npx cap add android` مستقبلي (أو إعادة
  توليد المشروع الأصلي) يمسحه، فيجب **إعادة وضعه يدوياً** فوق عنصر
  `<activity>` مباشرة بعد كل توليد، ثم التحقق أن `security-scan` أخضر.
  نفس القاعدة لأي تعديل يدوي داخل `android/` أو `ios/` (تُعاد من
  `capacitor.config.ts` عند التوليد).
- **الإرسال الخادمي — ما تبقّى (بلا صرف):** دالة `send-push` جاهزة
  في `supabase/functions/send-push/` لكنها لا ترسل شيئاً حتى يُضبط
  سرّ `FCM_SERVICE_ACCOUNT` (JSON حساب خدمة Firebase) في أسرار
  Edge Functions + تُنشَر الدالة:
  `supabase functions deploy send-push` (مع بقاء `verify_jwt` مفعّلاً —
  المتصل pg_cron بمفتاح الخدمة). إعداد حساب Firebase نفسه خطوة لوحة
  تحكم (مشروع Firebase + حساب خدمة) بلا صرف — ليست في هذا المستودع.
- أي فشل في التسجيل/المسح يُسجَّل في وحدة التحكم ولا يكسر التطبيق
  (المزايا الأصلية نائمة حتى يكتمل شقها الخادمي).

## الصيانة المزدوجة والترقيم (خطوة 6 — مسودة)

- مصدر واحد: نفس كود الويب يُنشر للويب (Vercel) وللتطبيق (مزامنة
  Capacitor) — لا فرع كود منفصلاً للتطبيق أبداً.
- **قاعدة الترقيم المثبتة (تصحيح غموض أشار إليه QA على PR #91):**
  التطبيق الأصلي يضمّ نسخة `dist` **المدمجة وقت المزامنة** — لا يحمّل
  محتوى ويب حياً (الكونفيج بلا `server.url`)، فتحديث ويب وحده **لا يصل
  إطلاقاً** للأجهزة المثبتة. أي تغيير — ويب أو أصلي — يصل للمستخدمين
  فقط عبر إصدار متجر جديد (رفع versionCode/versionName + مراجعة
  المتجر). الاستثناء الوحيد: تغيير أصلي بحت (إضافة/إعدادات/أذونات)
  يستلزم الإصدار نفسه؛ ولا يوجد مسار «تحديث ويب بلا متجر».
- كل إصدار متجر يمر بنفس بوابة QA الخاصة بإصدارات الويب + فحص 375px.
